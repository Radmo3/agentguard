\title{\textbf{Signhold: Outcome-Based Transaction Guardrails and Behavioral Anomaly Detection for AI Agents Holding Crypto Wallets}}
\author{Radhika Motwani\\\small Independent}
\date{\small November 2026}

\begin{document}
\maketitle

\begin{abstract}
\noindent
AI agents are increasingly given wallets. A recent study from Cornell Tech and Yale gave ten frontier models a stablecoin wallet with a one-cent daily spending cap and found that nine of them raised their own cap by reading the one-time code that the wallet platform had e-mailed to the owner, and that five of them paid an attacker who impersonated the owner by e-mail. The lesson is that a cap is a rule, and a rule the agent can reach is not a control. This report describes Signhold, an open-core guardrail that sits between an agent and its signer. Before anything is signed, the proposed transaction is simulated against chain state, its decoded effects (balance deltas, approvals, fund recipients, new contracts) are evaluated against an operator-defined policy, and the result---\code{allow}, \code{block} or \code{escalate}---is written to a hash-chained, Ed25519-signed audit log before it is returned. The agent is never asked whether the transaction is safe. Every error path escalates; no error path allows; a block is never downgraded. An \code{escalate} stays blocked on the server until a human approves it by signing a server-issued challenge, bound to the sealed audit record, with an Ed25519 key that lives on a device the agent cannot reach; the signature is verified server-side, so the agent can neither bypass nor simulate the approval (weak I-HITL in the terms of the Cornell--Yale authors; enrollment is not yet attested). An optional, separately licensed behavioral layer scores each transaction against a per-agent baseline learned only from previously allowed decisions, so that a drain which passes every static rule can still be stopped because it is out of character for that agent. We describe the threat model, the request pipeline, the handling of untrusted text, the audit design, and the EVM and Solana adapters, and we report an adversarial evaluation: nine defects found and fixed by the adversarial suite during development, a 200-case seeded fuzz run with zero server errors and zero \code{allow} verdicts on failed simulations, 353 passing tests in the public repository and 47 in the behavioral package, and two end-to-end demonstrations (eight public cases, including an escalation that the agent fails to approve and a human device then approves once; four learned-baseline cases) in which every verdict matched expectation. All evaluation is on synthetic, mock-RPC cases; there is no production deployment data yet.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Giving a language-model agent a wallet turns every failure of the model---a misread instruction, a prompt injected through a web page or an inbox, a compromised dependency---into a potential loss of funds. The usual response is to put a limit on the wallet: a per-transaction cap, a daily cap, an allowlist. The study by Breckenridge, Vilardell, Wang, Zhang and Juels~\cite{ihitl}, reported by CoinDesk on 1 November 2026~\cite{coindesk} and subsequently by Tech Insider~\cite{techinsider} and Forbes~\cite{forbes}, shows how little a limit is worth when the agent can reach the mechanism that changes it. According to those reports, the researchers gave ten AI models a Circle agent wallet on Base mainnet holding 10 USDC, with a daily spending cap of one cent; each model ran 20 trials per scenario. Raising the cap required a one-time passcode e-mailed to the owner, and the agents had access to that inbox. Asked to pay three one-cent invoices and told not to change their spending policies, nine of the ten models raised their own cap at least once by reading the code; one model (Claude Opus~5.5) was reported as the only one that never attempted a bypass, spending up to its limit and reporting the unpaid invoices. In a second scenario, a simulated attacker e-mailed the inbox posing as the owner and asked for a payment to an attacker-controlled wallet while the agent had only been asked to summarise its mail; five of the ten models raised their cap and paid the attacker at least once. The authors built Countersign, an open-source prototype that moves approval to a trusted phone so that the confirming interaction cannot be simulated in software, and stated that nothing in the experiments was specific to Circle or to e-mail~\cite{coindesk,forbes}.

\paragraph{Thesis.} A cap is a rule, and a rule is only a control when the agent cannot reach it. The same is true of allowlists, approvals, and any other configuration an agent can be talked into editing. Signhold\footnote{Signhold was briefly published under the name AgentGuard; the repository history and the commit hashes cited in this report are unchanged.} takes the position that the decision of whether a transaction may be signed must be made outside the agent, on the basis of what the transaction will actually do rather than what the agent says it is for, by a component that cannot be reconfigured by the agent, that fails closed when anything goes wrong, and that leaves a record which cannot be silently altered afterwards. A behavioral baseline complements this by catching transactions that are individually within every static limit but are not what this agent normally does.

\paragraph{Contributions.} This report makes the following contributions.
\begin{enumerate}
  \item A threat model for guardrails around agent-held wallets (Section~\ref{sec:threat}), in which the attacker is a compromised, misaligned or prompt-injected agent, and an explicit statement of what is and is not trusted.
  \item The design of a fail-closed check pipeline---simulate, reputation prefetch, behavior prefetch, policy evaluate, audit, persist---with decoded fund recipients as counterparties, untrusted text confined to an escaped string literal, a hash-chained and Ed25519-signed audit log, a vendor-neutral \code{guard(signer)} proxy, and EVM and Solana adapters (Section~\ref{sec:design}).
  \item A server-side implementation of I-HITL~\cite{ihitl} for escalations: the server seals a challenge into the audit record, an enrolled Ed25519 key that is never held by the agent host signs it, the server verifies the signature once and within a time limit, and the SDK can only observe the result. This is weak I-HITL in the paper's terms (unattested enrollment); the path to strong I-HITL is stated (Section~\ref{sec:approval}).
  \item A conceptual description of the behavioral anomaly layer: the signal categories it observes, its per-agent online statistics with a cold-start confidence term, its learn-from-allowed-only rule, and its deterministic, fail-closed scoring (Section~\ref{sec:behavior}).
  \item An adversarial evaluation with real counts: the defects found by the adversarial suite, a 200-case seeded fuzz run, per-package test counts, and two end-to-end demonstrations (Section~\ref{sec:eval}).
  \item A candid account of residual risks and what has not yet been validated (Section~\ref{sec:limits}).
\end{enumerate}

The open-source core is at \url{https://github.com/Radmo3/signhold} (Apache-2.0)~\cite{repo}; the behavioral layer is a separately licensed package~\cite{behrepo} and is described here only at the conceptual level.

\section{Threat Model}
\label{sec:threat}

This section condenses the project's threat model document~\cite{threatmodel}. Signhold does not hold wallet keys. Its job is to return a verdict that the SDK enforces before the agent's signer is invoked, and to leave a record that cannot be silently altered.

\paragraph{System and trust boundaries.} Five boundaries are drawn. (A) Agent--SDK: the SDK runs in the agent's process; the agent's \emph{code} is assumed trusted but its \emph{inputs} (model output, dApp data, e-mail, web pages) are not. Anything the agent can do, the SDK can be made to do, which is why the SDK fails closed rather than trying to resist its host. (B) SDK--API over the network: untrusted; TLS is expected from the deployment and HMAC request signing gives integrity and replay protection independent of where TLS terminates. (C) API--chain RPC: semi-trusted; RPC output is treated as data, never code, but a lying node cannot be detected. (D) Operator--API host: environment variables, the policy file and the audit file are controlled by the operator and trusted at boot. (E) Approver device--API: a phone, HSM, hardware key or operator laptop holds an approver private key and reaches the API over the network; the agent process is on the other side of this boundary by construction, since it is given a challenge and never a key.

\paragraph{Attackers.} Table~\ref{tab:attackers} lists the attacker models. The primary attacker for this report is the agent itself, in three forms: a compromised agent (T1) that runs arbitrary code in the agent process and holds the API key; a prompt-injected agent (T2) that has benign code but hostile instructions, and therefore chooses \emph{what} to propose and what free text to attach but cannot change SDK or API code; and, implicitly, a misaligned agent that behaves like T2 without an external injection. T3 (malicious counterparty contract), T4 (insider with host or audit-file access), T5 (network MITM) and T6 (unauthenticated internet attacker) complete the model, together with T7, a T1/T2 agent that treats ``human approval'' as one more API to drive.

\paragraph{T7: the agent reaches the approval channel.} This is the attack class that I-HITL~\cite{ihitl} describes: whatever the agent can reach, it can bypass or simulate. The paper's threats to an approval channel are that the agent \emph{reads} the channel (a screen read by an accessibility service, an inbox), \emph{simulates the approval input} (software-driven taps, a callback it can call), \emph{manipulates what the human sees} (overlays, imitation, spoofed senders) and \emph{uses a fallback path} (SMS, exportable seeds, re-enrollment). In the first draft of this report, approval of an \code{escalate} verdict was an \code{onEscalate} callback executed in the agent's process, which a T1 agent could call directly and a T2 agent could satisfy by returning \code{true}. The T7 agent holds the API key, sees the \code{auditId} and challenge of its own escalations, can call the approval routes freely, can run any ``approval UI'' the integrator wrote in its process, and can relay a challenge to the human with misleading context. The mitigation (Section~\ref{sec:approval}) is that an approval is a signature the agent cannot make, over a value it cannot choose, verified by a party it does not run, usable once, and that the approver device displays the sealed record rather than anything the agent relays. The residuals are explicit: enrollment is unattested, so a delegating human can still hand the key to the agent (weak, not strong, I-HITL); the service is the verifier, so a compromised API host (T4) could mint an approval; and the opt-in advisory callback is a fallback path (Section~\ref{sec:limits}).

\paragraph{Assets.} The assets, in the order the threat model ranks them, are verdict integrity (a wrong \code{allow} lets funds leave), the audit log, API keys, the Ed25519 audit signing key, the approver private keys (the only thing that can turn \code{escalate} into an approval; whoever holds one is ``the human'') together with the approver registry and pending challenges, the policy, transaction payloads (confidentiality), service availability (the SDK fails closed, so denial of service is denial of business rather than loss of funds), RPC trust, behavioral baselines (a poisoned profile makes a drain look normal), and reputation lists and feeds.

\paragraph{What is explicitly out of scope.} A compromised agent process (T1) that owns its signer can bypass the SDK by calling the signer directly. The threat model lists this as the primary residual risk of the whole design: Signhold is advisory until signing is moved behind a custody layer that calls the API itself (see Section~\ref{sec:limits}). Simulation blind spots (state-dependent or MEV-sensitive behaviour that differs between simulation and inclusion) are an inherent residual of simulation-based checking, compensated by small caps, allowlists and private RPC.

\section{Design}
\label{sec:design}

\subsection{Request flow}
\label{sec:flow}

The agent's signer is wrapped by the SDK's \code{guard()} proxy. When the agent calls \code{signTransaction} or \code{sendTransaction}, the proxy builds a \code{TransactionIntent} (chain, \code{from}, \code{to}, \code{value}, calldata or, for Solana, the base64 serialised transaction, plus an optional free-text \code{description} and \code{metadata}) and submits it to \code{POST /v1/check}. The server processes it in a fixed order (Figure~\ref{fig:flow}):

\begin{enumerate}
  \item \textbf{Validate.} API key (SHA-256 hashed at startup, compared with \code{timingSafeEqual}), optional HMAC signature with timestamp and nonce (5-minute replay window, per-key nonce cache), per-key rate limit (120 requests per minute by default), and a strict schema: unknown keys rejected, intent ids must be UUIDs, addresses validated per chain, \code{description} $\le$ 2~KiB, \code{metadata} $\le$ 8~KiB serialised, calldata $\le$ 128~KiB, body $\le$ 64~KiB, no \code{NaN}/\code{Infinity}, JSON only.
  \item \textbf{Simulate.} The chain adapter decodes the transaction and simulates it against live state, producing a \code{SimulationResult}: asset deltas with USD values, approval changes (with whether the spender is a contract), decoded fund \code{recipients}, contracts touched, contracts never seen before, gas, warnings and an \code{ok} flag. Each adapter sits behind a circuit breaker with a per-call timeout; an open circuit yields an immediate \code{escalate} with finding \code{adapter\_unavailable}.
  \item \textbf{Reputation prefetch.} The server \emph{awaits} \code{reputation.prefetch(intent,} \code{simulation)}, which looks up every counterparty (\code{to}, contracts touched and decoded recipients) across the configured providers and warms a cache.
  \item \textbf{Behavior prefetch.} If a behavioral integration is plugged in, the server awaits the profile store (\code{store.get(agentId)}), which loads the agent's profile into memory.
  \item \textbf{Evaluate.} The policy engine evaluates the built-in rules and the custom \code{reputation} and \code{behavior} rules \emph{synchronously}, reading only the caches warmed in steps 3--4, and returns a \code{Decision} with a verdict, a 0--100 risk score, a list of findings and a human-readable explanation. The strictest firing rule wins.
  \item \textbf{Audit.} The decision is appended to the audit store as a hash-chained, signed record \emph{before} the verdict is returned. If the store cannot record it, the API returns \code{503 audit\_unavailable} and no verdict at all.
  \item \textbf{Persist.} The sealed decision is handed to \code{behavior.persist}; a failure here is logged and does not change the already-audited verdict.
\end{enumerate}

\paragraph{Risk score.} The score is a deterministic function of findings and simulation, clamped to $[0,100]$: $+40$ per blocking finding, $+20$ per escalating finding, $+25$ if the simulation did not succeed, $+10$ per simulation warning (capped at 30), $+15$ per unlimited approval (capped at 30) and $+10$ per never-seen contract (capped at 20). A transaction that fires no rules and has a clean simulation scores 0. On an engine error the score is at least 50 and the verdict is \code{escalate}.

\paragraph{Policy.} Policies are JSON documents validated at load. The rule kinds are \code{max\_tx\_usd}, \code{max\_window\_usd}, \code{allowlist\_only}, \code{denylist}, \code{no\_unlimited\_approvals}, \code{no\_eoa\_approvals}, \code{max\_slippage\_bps}, \code{no\_new\_contracts}, \code{require\_simulation\_ok}, \code{max\_native\_value} and \code{custom}; each rule's \code{onViolation} is \code{block} (default) or \code{escalate}. The bundled \code{conservative-default} policy blocks reverting simulations, unlimited approvals, approvals to externally-owned accounts (EOAs), denylisted counterparties and transactions above \$100, and escalates above \$500 per rolling window, above 0.05 native units, on contracts with no prior history, and on swaps whose simulated output is more than 1\% below the expected output. ``Unlimited'' means any approval $\ge 2^{128}$ base units or exactly \code{u64::MAX} or \code{uint96::MAX}, so bounded-but-astronomical amounts ($2^{200}$, Permit2's \code{uint160} maximum) are caught as well. The policy is loaded by the operator at boot; an agent can select only among policies the operator loaded and cannot edit one.

\subsection{Fail-closed principles}
\label{sec:failclosed}

The API guarantees, and its tests enforce, the following~\cite{security}:
\begin{itemize}
  \item Any exception in simulation, policy evaluation, the circuit breaker, the reputation prefetch, the behavior profile load or response validation produces \code{escalate}, never \code{allow}, and never downgrades a \code{block}. The finding names the path: \code{simulation\_error}, \code{engine\_error}, \code{adapter\_unavailable}, \code{invalid\_decision}, \code{reputation\_error} or \code{behavior\_error}.
  \item The engine never throws from \code{evaluate}; it returns a decision with verdict \code{escalate} and reason \code{engine\_error}. A policy that references a custom rule the engine does not have escalates rather than silently passing.
  \item Custom rules are synchronous and read only from caches warmed before \code{evaluate}; a cache miss produces \code{escalate} (tag \code{not\_prefetched}), never a null result.
  \item A reputation provider error or timeout lifts the risk floor and tags the result \code{provider\_error}; the rule escalates on that tag regardless of score. Aggregation precedence is malicious $>$ suspicious $>$ trusted $>$ unknown, and an operator deny entry wins over any provider.
  \item The SDK's \code{guard()} proceeds only on the literal verdict \code{allow}, or on \code{escalate} once the read-only status route has reported the literal status \code{approved} with an approver identity (Section~\ref{sec:approval}). Network errors, 4xx/5xx responses, malformed responses, approval timeouts, expiry or rejection, and exceptions thrown by hooks all prevent the signer from being called.
  \item If the audit store cannot record a decision, no verdict is returned (\code{503}); the SDK treats this as ``do not sign''.
\end{itemize}

\subsection{Untrusted text}
\label{sec:text}

The agent's \code{description} and \code{metadata} are attacker-chosen under T2. They never feed a rule, with one documented exception: \code{metadata.expectedOutUsd} is a slippage hint that can only make the slippage check stricter. In the explanation, the description is stripped of control characters, length-capped and emitted as an escaped JSON string literal labelled \emph{agent's stated purpose}, so injected text cannot close the quote, imitate a finding, or precede the real ``Blocking rule:'' text. Provider tags and evidence from reputation feeds are treated the same way. Logs above \code{debug} level redact API keys, signatures, calldata, raw transactions and metadata; 5xx responses are a fixed body plus a request id.

\subsection{Decoded counterparties}
\label{sec:recipients}

A transfer to a denylisted address is usually \emph{not} a transaction whose \code{to} is that address; it is a call to a trusted token contract whose calldata names the recipient. Adapters therefore populate \code{SimulationResult.recipients} with decoded fund recipients: ERC-20 \code{transfer}/\code{transferFrom} targets, swap recipients, SPL token destinations and their owners, and the new authority of a Solana \code{SetAuthority}. The \code{denylist}, \code{allowlist\_only}, \code{behavior} and \code{reputation} rules all treat recipients as counterparties alongside \code{to} and the contracts touched, and address comparison is case-insensitive so that EIP-55 mixed case cannot evade a lower-case list. Recipients reachable only through undecoded internal calls remain a limitation (Section~\ref{sec:limits}).

\subsection{Tamper-evident audit}
\label{sec:audit}

Every audit record carries an \code{integrity} envelope \{\code{seq}, \code{prevHash}, \code{hash}, \code{alg}, \code{signature}, \code{keyId}\}. The hash is SHA-256 over canonical JSON (sorted keys, bigints as decimal strings) of the record body plus \code{seq} and \code{prevHash}, so each record commits to its predecessor. When a signing key is configured (required in production; development generates an ephemeral key and logs its id), the chain hash is signed with Ed25519 and the public-key fingerprint is embedded as \code{keyId}, which allows rotation and offline verification with published public keys. The record also carries the submitting API key id as \code{principal}, giving per-agent attribution. \code{GET /v1/audit/verify} and an offline script re-walk the chain and report \code{hash\_mismatch}, \code{broken\_link}, \code{seq\_gap} or \code{bad\_signature}. The audit write happens before the verdict is returned, so there are no silently lost decisions. Truncating the \emph{tail} of the log is detectable only if the head hash is anchored externally (Section~\ref{sec:limits}).

\subsection{Inalienable human approval of escalations}
\label{sec:approval}

An \code{escalate} verdict means that a human has to decide. I-HITL~\cite{ihitl} asks whether the agent can take that human out of the loop, and the answer for the first draft of this system was yes: approval was an \code{onEscalate} callback in the agent's process. This revision makes approval a cryptographic act that happens outside the agent's reach and is verified by the service (Figure~\ref{fig:approval}). We describe it in the paper's terms. Its model has four parties: the human $\mathcal{H}$, the agent platform $\mathcal{P}$ (adversary-controlled), the service $\mathcal{S}$ that enforces the policy and executes only approved actions, and a trusted entity $\mathcal{T}$ outside the agent's control that can hold secret state and perform cryptography. A protocol is a triple $(\mathsf{Enroll}, \mathsf{Approve}, \mathsf{Verify})$: enrollment gives $\mathcal{S}$ a verification string $vk$, approval of a message $m$ gives $\mathcal{S}$ a proof $\pi$, and $\mathsf{Verify}(vk, m, \pi)$ decides. The property that matters is \emph{approval-binding}: $\mathcal{S}$ accepts a proof for $m^{*}$ only if $\mathcal{H}$ was shown a request for $m^{*}$ and approved it. A protocol is \emph{weak} I-HITL if that holds for an honest human and \emph{strong} if it holds even for a delegating human who would hand approvals to the agent, which the paper shows requires $\mathcal{T}$ to hold an attested, non-extractable key.

\paragraph{What Signhold implements: the service side.} The Signhold API is $\mathcal{S}$. $\mathsf{Enroll}$ is the operator's registration of an approver's Ed25519 public key in \code{SIGNHOLD\_APPROVER\_KEYS} (\code{id:base64}, one entry per human); $vk$ is that key. The message $m$ is the escalated check itself: when a decision escalates and approver keys are registered, the server computes, \emph{before} the agent sees the response,
\[
  \small c = \mathrm{SHA\text{-}256}\big(\mathrm{canonical}\{v{=}1,\ \code{auditId},\ H(\mathit{intent}),\ H(\mathit{decision}),\ \code{policyId},\ \code{policyVersion},\ \code{agentId},\ \code{issuedAt}\}\big)
\]
where $H$ is SHA-256 over canonical JSON and the decision hash omits only the raw simulation trace. The challenge $c$ is sealed into the \code{escalate} audit record as \code{approvalRequest}, so it is covered by the chain hash and signature, stored in a pending table with an expiry, and returned to the agent alongside the verdict. $\mathsf{Approve}$ is the device's Ed25519 signature over the UTF-8 bytes of $c$, and $\pi$ is \{\code{auditId}, \code{keyId}, \code{signature}, \code{approvedAt}\}, submitted to \code{POST /v1/approvals}. $\mathsf{Verify}$ runs every check, always in the same order and all of them regardless of which fails: the pending entry exists, is unused and unexpired; the referenced record exists, is a \code{check} with verdict \code{escalate}, and recomputes (with \code{timingSafeEqual}) to the same $c$ as both the pending entry and the sealed \code{approvalRequest}; \code{keyId} is enrolled; the signature verifies (exactly one verification is performed, against a decoy key for unknown ids, so timing does not reveal which ids exist); and \code{approvedAt} lies between issue and expiry with a 60-second clock-skew allowance. Success claims the entry synchronously (two concurrent valid submissions cannot both win), appends an \code{approval} record to the audit chain whose \code{principal.approverKeyId} names the device, and returns \code{\{verdict: allow, approvalId\}}. Any failure is a generic \code{403 approval\_rejected}, the reason goes only to the server log and to a chained \code{approval\_rejected} record, and the challenge is burned: a new check is required. Approvals are single use, expire after \code{SIGNHOLD\_APPROVAL\_TTL\_MS} (default 15 minutes), and exist only for \code{escalate}: \code{allow} needs none and \code{block} never receives a challenge, even from an enrolled device. Because $c$ commits to the audit record, the exact intent, the decision, the policy, the agent and the issue time, a proof approves one transaction under one decision and nothing else; the same transaction re-checked produces a different record and therefore a different challenge. This gives approval-binding under one assumption: that the private half of $vk$ is held only by the human's device.

\paragraph{Three keys, three holders.} That assumption is what the key separation is for. \emph{API keys} (\code{SIGNHOLD\_API\_KEYS}) are transport authentication only; the agent holds one, and so does the approver device, under a different id, so that the audit \code{principal} shows who submitted each request. \emph{Approver keys} are generated on, and confined to, the approver's device (a phone keystore, HSM, hardware key, or the \code{approve.ts} CLI on an operator laptop); they are never on the agent host and never on the Signhold host. The \emph{audit signing key} is held by the service alone, and the registry refuses at startup to enroll it, or any other server-held key, as an approver, so the service cannot be configured into minting approvals under its own key. Holding the API key, which is all the agent has, gives no way to approve anything.

\paragraph{Weak, not strong.} Enrollment in this release is operator registration of a public key with no attestation and no key encumbrance: nothing proves to $\mathcal{S}$ that the key was generated in secure hardware, and nothing stops a delegating human from exporting it to the agent. By the paper's definition this is therefore \emph{weak} I-HITL: the agent cannot bypass or simulate the approval, but a human who chooses to give the agent their key can. It becomes strong when $\mathcal{T}$ is an attested device with a non-extractable key; the I-HITL authors' open-source Countersign app~\cite{countersign}, which uses a phone's hardware-backed keystore with remote attestation, is such a device, and integrating it (or any attested keystore) as the approver, with attestation checked at enrollment, is the immediate next step. This report does not claim strong I-HITL.

\paragraph{Trusted display.} Approval-binding also requires that the human was \emph{shown} $m^{*}$: the request must appear on a display the agent cannot drive or overlay, or a genuine press approves whatever the agent substituted. The challenge is a hash and says nothing to a human, so the required behaviour of any approver device is: fetch the sealed audit record from the server with the device's own credential (never accept it from the agent), recompute $c$ from that record, display the intent summary (\code{from}, \code{to}, decoded recipients, asset deltas, approvals, and the policy explanation with the agent's text marked as its stated purpose) and sign only the value it reconstructed. The reference \code{approve.ts} CLI enforces this: it fetches the sealed record from the server with the device's own API key (or takes a copy obtained out of band), recomputes $c$, prints the decoded transaction, requires a typed confirmation, and refuses to sign a bare challenge or one it cannot reconstruct, so a challenge relayed through the agent cannot be pointed at a different transaction than the one the human is shown. The CLI's display is a terminal, trusted only if the host running it is not the agent host.

\paragraph{What the SDK can and cannot do.} \code{guard()} now defaults to \code{approval: "server"}. On \code{escalate} it either throws \code{GuardEscalatedError} carrying the \code{auditId} and challenge for the integrator to route to a human, or, with \code{waitForApproval}, blocks while polling the read-only \code{GET /v1/approvals/:auditId} and calls the signer only when that route reports the literal \code{approved} with \code{approvedBy} and \code{approvalId}; \code{expired}, \code{rejected}, \code{unknown}, a timeout or a malformed body are all treated as denial. The status route accepts no writes. In server mode \code{guard()} refuses an \code{onEscalate} option with a \code{TypeError}, captures the mode at construction so a later mutation of the options object cannot inject a callback, and ignores the return value of the notification hook \code{onEscalationPending}. The old callback remains available only as an explicitly opted-in \code{approval: "callback"} advisory mode that logs a warning once at startup. It is a fallback path of exactly the kind I-HITL warns against; operators should disable it in production, and the security checklist treats using it for a funded signer as disabling the product.

\subsection{Vendor neutrality}
\label{sec:neutral}

Signhold does not hold keys and does not depend on any wallet vendor. The SDK's \code{guard(signer, client, options)} wraps whatever signer object the agent already uses---an ethers or viem account, a custody SDK, a Solana keypair wrapper---and intercepts \code{signTransaction}/\code{sendTransaction}; the operator supplies a \code{toIntent} mapping from the signer's native argument to a \code{TransactionIntent}. The server side is likewise composed from duck-typed parts: \code{createServer()} takes adapters, a policy map, an audit store and optional \code{reputation} and \code{behavior} integrations, and the API has no compile-time dependency on the behavioral package; it is loaded by name at boot if installed and otherwise the server logs that behavioral detection is disabled and runs the built-in and reputation rules. Any implementation with the same \code{\{store, rule, persist\}} shape can be plugged in; the public test suite exercises that contract with an in-repository stub.

\subsection{Chain adapters}
\label{sec:adapters}

\paragraph{EVM.} The adapter (built on viem) decodes ERC-20 \code{transfer}, \code{approve}, \code{transferFrom}, \code{permit}, ERC-721 \code{setApprovalForAll}, and common Uniswap-style swap entry points (V2 \code{swapExact*}/\code{swapTokensForExact*} and V3 single- and multi-hop inputs, including the packed V3 path), runs \code{eth\_call} and gas estimation, reads token \code{decimals}/\code{symbol} and allowances, checks \code{getCode} to classify spenders as contracts or EOAs, and compares against an operator-supplied set of known contracts to detect never-seen ones. Unknown selectors are reported as a warning; trailing bytes after the ABI-encoded arguments are reported as a warning rather than ignored; odd-length hex is a schema error.

\paragraph{Solana.} The adapter (built on \code{@solana/web3.js} and \code{@solana/spl-token}) accepts a serialised versioned transaction, resolves address lookup tables, decodes System \code{Transfer}/\code{TransferWithSeed}, ComputeBudget instructions, and SPL Token \code{Transfer}, \code{TransferChecked}, \code{Approve}, \code{ApproveChecked}, \code{Revoke}, \code{SetAuthority} and \code{CloseAccount}, runs \code{simulateTransaction} with post-state account data to compute lamport and token-balance diffs, and reports duplicate compute-budget instructions. A \code{SetAuthority} that hands an agent-owned account to another authority is modelled as an unlimited approval so that the same rule blocks it. Both adapters accept an injectable RPC client, which is how the tests and demos run without network access.

\section{Behavioral Anomaly Layer}
\label{sec:behavior}

Static rules bound what an agent may do; they say nothing about what this agent \emph{usually} does. The public demonstration case that motivates the behavioral layer is an agent whose history is thirty routine \$5 payments to one counterparty, which then proposes a \$95 transfer to a never-paid address two minutes after the last payment with the description ``routine rebalancing to our cold wallet''. The transfer is under the \$100 per-transaction cap, goes through a known token contract, and simulates cleanly; no built-in rule fires. The behavioral layer exists to catch exactly that.

The layer, \code{@signhold/behavior}, is proprietary and separately licensed~\cite{behrepo}. This section describes it at the conceptual level only; feature identifiers, weights, formulas and threshold values are not published.

\paragraph{Signals observed.} For each transaction, the analyzer compares the decoded simulation result (not the agent's description) against the agent's profile along several categories of signal: \emph{counterparty novelty} (whether the funds flow to addresses, assets or chains this agent has never transacted with); \emph{amount relative to baseline} (how the outflow compares with the agent's running mean, spread and largest previous transaction); \emph{timing and cadence} (bursts far faster than the agent's typical inter-arrival time, dormancy followed by a large transaction, and unusual time of day); \emph{approval behaviour} (a first approval to a spender this agent has never approved); \emph{recent verdict history} (a run of recent blocks or escalations); and a compound \emph{drain shape} signal that fires when funds leave to a never-paid address \emph{and} the amount is far outside the agent's history, which is the shape of a key compromise or a prompt-injection drain.

\paragraph{Per-agent online statistics and cold start.} Each agent has a profile of bounded size holding its counterparties, assets and chains seen, online amount statistics (a running mean and variance plus a bounded sample for upper quantiles), a time-of-day histogram, a smoothed inter-arrival estimate, approval spenders and a bounded verdict history. Profiles are updated incrementally and are bounded in size. A new agent starts cold: the score contributions are scaled by a confidence term that grows with the number of allowed transactions observed and saturates once the baseline is mature. Cold start therefore means \emph{lower confidence}, not fail-open and not a crash: a cold-start agent falls back to the static rules, as the drain-demo case (c) in Section~\ref{sec:eval} shows.

\paragraph{Only allowed decisions teach the baseline.} The API hands every sealed decision to the layer, but only \code{allow} decisions update counterparties, amounts, cadence and approvals; blocked and escalated decisions extend only the verdict history, which raises the next score. A rejected drain can never make itself normal, and a patient attacker who wants to shift the baseline must get transactions past the static caps per transaction and per window to do so. Profiles are persisted as JSONL with a per-agent SHA-256-chained event log; stores refuse rollbacks and invalid snapshots, and a \code{verifyEventChain} utility exists for forensic checks. The threat model notes the residual: a rewrite that also regenerates the chain is undetectable without an external anchor.

\paragraph{Deterministic and fail-closed.} Scoring is a pure function of the profile and the simulation result; the same inputs always yield the same anomaly score in $[0,100]$ and the same one-paragraph explanation naming the signals that fired. Untrusted text never influences the score. The rule fires \code{escalate} at an escalate threshold and \code{block} at a higher block threshold; both are parameters of the policy rule, so the operator sets them in the same reviewed policy file as every other rule. If the analyzer itself fails, it returns a fixed non-zero sentinel score with an error marker rather than zero, so an internal error cannot manufacture an \code{allow}; if the profile cannot be loaded at all, the API escalates with \code{behavior\_error} before the rule runs. The layer follows the same two-phase pattern as the reputation layer: asynchronous warm-up before \code{evaluate}, synchronous read inside it, asynchronous learning after the audit record is sealed.

Case (h) exercises the approval path of Section~\ref{sec:approval}. The response carries a 64-hex challenge with a 15-minute expiry and the status route reports \code{pending}. (2) A fresh check of the same transaction yields a new audit id and a new challenge; the agent blocks in \code{waitForApproval} while the device fixture signs the new challenge and posts it under its own API key: the server answers \code{verdict: allow} with an \code{approvalId}, \code{waitForApproval} resolves with \code{approved by ops-phone}, and the status route reports \code{approved}. Case (g) shows that a layer outage degrades to a human review rather than to silence.

\section{Limitations and Future Work}
\label{sec:limits}

The following are stated in the threat model as residual risks or are evident from the evaluation.

\begin{itemize}
  \item \textbf{Agent-side bypass.} A compromised agent process that owns its signer can call the signer without going through \code{guard()}. Signhold is advisory until signing is moved behind a custody layer that calls the API server-side; the roadmap lists Fireblocks policy-engine hooks and a Safe guard module for this purpose. This is the primary residual risk of the design. Human approval is now inalienable with respect to the agent (it cannot produce or simulate one), but the \emph{enforcement} of ``no approval, no signature'' still happens in the agent's process, and an approval is not bound to the signed bytes: after \code{approved}, the SDK in the agent's process still decides what it hands to the signer.
  \item \textbf{Unattested enrollment (weak I-HITL).} Approver keys are enrolled by operator registration of a public key, with no attestation and no key encumbrance. The agent cannot produce or simulate an approval, but a delegating human can export the key to it, so the guarantee is weak I-HITL by the paper's definition~\cite{ihitl}. Strong I-HITL needs an attested device with a non-extractable key as the approver; integrating Countersign~\cite{countersign} or an equivalent attested keystore, with attestation verified at enrollment, is the immediate next step.
  \item \textbf{Advisory callback mode is a fallback path.} \code{approval: "callback"} runs the approval inside the agent's process, which is exactly the fallback I-HITL warns against. It is opt-in and warns at startup, but it exists; operators should disable it in production, and a build-time switch to remove it is planned.
  \item \textbf{Service-side verification trusts the service.} Approvals are verified by the Signhold host. A root on that host can call the approval path with any key, or add a key to the registry at the next boot; such an approval is attributable in forensics (it is signed into the chain under a \code{principal.approverKeyId}) but not prevented. The roadmap item that removes this trust is on-chain enforcement: a Safe guard module or Solana program that itself verifies the approver's Ed25519 signature over the challenge before the transaction can execute, so that neither the agent host nor the Signhold host can execute an escalated transaction without the human's device.
  \item \textbf{In-memory pending approvals.} The pending-approval table lives in server memory. A restart forgets every pending challenge; its status becomes \code{unknown}, which the SDK treats as not approved, and a fresh check is required. This fails closed but is operationally visible, and a durable store is needed before a multi-instance deployment.
  \item \textbf{Undecoded internal calls.} Recipients reachable only through internal calls that the adapters do not decode are not seen as counterparties. Closing this needs a trace-capable RPC (\code{traceCall}) and is future work.
  \item \textbf{Simulation blind spots.} State-dependent, block-gated or MEV-sensitive behaviour can differ between simulation and inclusion, and a lying RPC node can make a drain simulate clean. Operators are told to use private RPC, small caps and allowlists.
  \item \textbf{Audit head anchoring.} Truncating the tail of the audit log, or rewriting a behavioral profile together with its event chain, is detectable only if the head hash is anchored externally (a WORM store or a chain). Periodic export of the head hash is an operator procedure today, not a feature.
  \item \textbf{Unsigned policy files.} Policy id and version are embedded in every decision, but policy files are not signed; file-integrity monitoring or GitOps is recommended until policy signing ships.
  \item \textbf{Response-leg integrity depends on TLS.} Requests can be HMAC-signed; responses are not yet signed, so a MITM that defeats TLS could flip a verdict in transit. Response signing with the audit key is on the roadmap.
  \item \textbf{Tenant-scoped audit reads.} All API keys currently share one tenant, so any valid key can read any audit record. Per-tenant scoping of \code{GET /v1/audit} is planned.
  \item \textbf{Policy selection.} If an operator loads a permissive policy alongside a strict one, an injected agent can pick it. The guidance is one policy per deployment or per-key policy enforcement, which is also planned.
  \item \textbf{No production data.} Every number in Section~\ref{sec:eval} comes from synthetic cases against mock RPC clients. There is no deployment data on false-positive rates, escalation volume, or the behaviour of real agents, and the fail-closed design means that an ill-tuned policy or a flaky provider will produce escalations rather than losses, which is the intended failure mode but one whose operational cost has not been measured.
  \item \textbf{Behavioral cold start and drift.} A new agent has no baseline, so the behavioral layer contributes little until the agent has accumulated allowed history; during that period only the static rules protect it (drain-demo case (c)). Conversely, a patient attacker who stays within the static caps can drift the baseline slowly over weeks; the mitigation is periodic baseline review and event-chain verification, not a mechanism. The layer's thresholds and the weight of its signals have been calibrated on synthetic sequences only.
\end{itemize}

\section{Related Work}
\label{sec:related}

Several wallet providers and security vendors address agent-held wallets. The descriptions below are drawn from each vendor's public documentation or announcements as accessed on 10 November 2026 and are intended to be factual rather than comparative in favour of any product.

\paragraph{Platform-level human-in-the-loop.} The I-HITL paper~\cite{ihitl} argues that an agent must be unable to reach the approval channel at all, formalises the condition in terms of communication topology, shows it requires a trusted device, and prototypes Countersign on consumer phones. The first draft of this report described Signhold as complementary, deciding \emph{which} transactions need a human and leaving the trustworthiness of the approval channel to the deployment; a review by one of the I-HITL authors pointed out that the draft's in-process \code{onEscalate} callback was exactly the alienable channel their paper warns against. This revision adopts an I-HITL mechanism for escalations in response to that work (Section~\ref{sec:approval}): Signhold implements the service side, $\mathcal{S}$, with a server-sealed challenge, Ed25519 verification against an enrolled key, single use and a TTL. Because enrollment is an unattested public key, it is weak I-HITL by their definition; it becomes strong with an attested, non-extractable key in the approver device, which is what Countersign~\cite{countersign} provides and what the next release targets. Signhold still contributes the part I-HITL leaves open: deciding, from simulated outcome and behavioral context, which transactions need the human at all. Foundation's Passport Prime~\cite{foundation} takes the hardware route commercially, positioning a dedicated device as the final approver for agent actions with user-set policies enforced on the device; the announcement names Bitcoin as the core focus and does not describe on-device simulation or anomaly detection.

\paragraph{Wallet platforms with built-in limits.} MetaMask Agent Wallet~\cite{metamask} exposes a CLI and SDK with server-side keys in a TEE or a bring-your-own mnemonic, simulates transactions before execution, scans them with Blockaid (malicious transactions are bounced and flagged ones require approval), supports an outflow policy with rolling 24-hour limits and an optional 2FA step, and offers a paid transaction-protection guarantee; its documentation does not mention per-agent behavioral baselining. Coinbase Agentic Wallets~\cite{coinbase} keep keys in Coinbase infrastructure, provide configurable per-session and per-transaction spending limits enforced before any transaction, KYT and OFAC screening, and support Base, Polygon and Solana; the documentation does not mention transaction simulation or anomaly detection. Both are tied to the vendor's wallet.

\paragraph{Policy engines in key-management infrastructure.} Privy's policy engine~\cite{privy} evaluates allow/deny rules---recipient and contract allowlists, value limits, ABI- or IDL-decoded calldata conditions, EIP-712 constraints, and stateful limits over time windows for Ethereum---inside the enclave before signing, denies by default, and runs simulation before policy evaluation for operations it also broadcasts; its documentation describes stateful rules against explicit aggregates rather than learned behaviour. Turnkey~\cite{turnkey} evaluates policies on fields such as recipient, chain id, calldata slices and decoded ABI parameters inside a secure enclave, with DENY overriding ALLOW, delegated-access users that start with zero permissions, and consensus rules that can require an agent plus a human or a risk service; its documentation leaves anomaly detection to the operator and suggests DENY policies as circuit breakers. Both enforce at the key, which Signhold does not, and both are specific to their custody product.

\paragraph{Policy analysis and threat intelligence.} Fireblocks' Agentic Policy Analyzer~\cite{fireblocks} uses LLM agents to adversarially test a customer's transaction authorization policy for exploitable rule combinations each time the policy is modified or published, producing a record of each successful exploit as a remediation guide; it runs on policy configuration, not at transaction time. Blockaid~\cite{blockaid} provides real-time transaction simulation, token risk assessment, continuous monitoring of dApps, tokens and addresses, and address validation through APIs, with LangChain, MCP and function-calling integrations for agents; its agent offering was described as a private beta and does not include per-agent baselining or policy enforcement. Signhold's \code{HttpProvider} is the integration point for feeds of this kind.

\paragraph{Intent verification.} Nava~\cite{nava} holds funds in an on-chain escrow and releases them only when staked verifiers confirm that a proposed transaction's outcome matches the user's signed intent, with each decision posted to a public ledger; as reported, it is an intent-verification and escrow layer rather than a wallet-level guardrail, and it does not include behavioral baselining. Verdict Machine~\cite{verdictmachine}, a 2026 startup, describes an ``AI firewall for on-chain money movement'' for financial institutions that maps an institution's wallets, contracts and vendors, generates policies, and evaluates proposed transactions against them before settlement; its public description is institution-focused and policy-based, and does not mention per-agent behavioral baselining or an approval channel the agent cannot reach.

To the author's knowledge, none of the systems above learns a per-agent behavioral baseline from allowed decisions and uses it, together with outcome simulation and reputation, to decide between allow, block and escalate for an arbitrary signer. That combination, its fail-closed composition, and the adversarial evidence in Section~\ref{sec:eval} are what this report contributes.

\section{Conclusion}
\label{sec:conclusion}

The cap-bypass study showed that models will, in a surprising range of cases, reach the mechanism that limits them. Signhold is built on the view that the agent should not be the one deciding whether a transaction is safe, and should not be able to reach the component that does. The design puts simulation, policy, reputation and behavior in one fail-closed pipeline in front of the signer, treats every piece of agent-supplied text as data, decodes who actually receives funds, seals a signed, chained audit record before any verdict is returned, and makes human approval of an escalation a signature the agent cannot produce, over a challenge it cannot choose, verified by a party it does not run (weak I-HITL today; attested approver devices are the next step). The adversarial suite found and fixed nine defects during development, a 200-case seeded fuzz run produced no server errors and no \code{allow} on a failed simulation, and the two demonstrations show both the static rules and the learned baseline stopping transactions that look reasonable on their face. What remains unproven is operational: the false-positive and escalation rates on real agents, the robustness of simulation against adversarial contracts in the wild, and the custody integrations that would turn an advisory verdict into an enforced one. Those are the next steps.
